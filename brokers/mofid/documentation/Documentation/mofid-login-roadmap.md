# نقشهٔ راه ورود مفید به Trading_bot

## هدف و محدوده

این نقشه برای حل مرحله‌ای قرارداد ورود مفید و افزودن حساب مفید به برنامه است. تصمیم معماری کاربر برای مرحلهٔ ۲ ثبت شد: Trading_bot می‌تواند جریان OIDC وب را با HTTP client دنبال کند، code را از redirect نهایی بگیرد و callback وب را بارگذاری نکند. این تصمیم به‌تنهایی مجوز ورود واقعی یا درخواست تازه به مفید نیست. همهٔ شواهد باید پاک‌سازی‌شده باشند: فقط نام فیلدها، نوع داده، مسیر، روش، status و معنای پاسخ؛ بدون رمز، OTP، CAPTCHA، token، cookie، header احراز هویت، شناسهٔ شخصی یا دادهٔ واقعی حساب.

## ترتیب کار

### 1. قرارداد پاسخ `same-login`

**وضعیت: پاسخ موفق مشاهده شد؛ رفتار خطا هنوز نامشخص است.** در Network نشست فعلی، درخواست طبیعی `POST https://api-mts.orbis.easytrader.ir/easy/api/account/same-login` با HTTP `200` دیده شد و پاسخ آن body خالی داشت. درخواست `application/json` بود و schema ساختاری آن `{uuid:string, appBuildNo:string, width:number, height:number, devicePlatform:string, platformInfo:string}` است؛ مقادیر درخواست در این سند ثبت نمی‌شوند. بنابراین در نمونهٔ موفق مشاهده‌شده، علامت قابل اتکا همان status `200` همراه پاسخ خالی است؛ فیلد معنایی در body وجود نداشت. این capture دربارهٔ statusها یا پاسخ‌های ناموفق نتیجه‌ای نمی‌دهد. هیچ درخواست جدیدی از طرف بررسی‌کننده ارسال یا بازپخش نشد.

**پرسش:** پاسخ موفق و ناموفق این درخواست چه ساختاری دارد و برنامه از کجا می‌فهمد نشست مجاز است؟

**روش بررسی:** از شواهد مستند موجود و در صورت نیاز فقط از سابقهٔ طبیعی Network که کاربر قبلاً ایجاد کرده استفاده شود. body خام یا مقادیر آن استخراج نشود؛ فقط شکل ساختاری پاک‌سازی‌شده ثبت شود. هیچ درخواستی بازپخش یا دستی ارسال نشود.

**خروجی لازم:** نام/type فیلدهای پاسخ در حالت‌های مشاهده‌شده، status HTTP، معنا و اثر هر حالت، و تفکیک «مشاهده‌شده» از «نامشخص».

**معیار پایان:** بتوان پاسخ را بدون حدس به موفق/رد/نامشخص نگاشت کرد؛ اگر شواهد برای حالت خطا وجود ندارد، آن حالت صریحاً باز بماند. شاخهٔ موفق این معیار برای یک نمونه بسته شد: HTTP `200` و body خالی. پاسخ خطا و سایر statusها همچنان نامشخص‌اند و برای تکمیل این شاخه، capture طبیعی بیشتری فقط در صورت وقوع عادی لازم است؛ درخواست خطا عمداً تولید نشود.

### 2. امکان اجرای OIDC از فرم برنامه

**ارزیابی این گام کامل شد؛ نتیجهٔ امکان اتصال مستقیم هنوز اثبات نشده است.** Network نشست دستی تأیید کرد که EasyTrader از OIDC authorization code استفاده می‌کند و PKCE با `S256` را در authorize درخواست می‌کند. callback مشاهده‌شده `https://d.easytrader.ir/auth-callback` است. token exchange شامل نام فیلدهای `grant_type`, `redirect_uri`, `code`, `code_verifier`, `client_id` بوده و پاسخ `200 application/json` دارای کلیدهای `id_token`, `access_token`, `expires_in`, `token_type`, `scope` است؛ هیچ مقدار محرمانه‌ای در این نقشه ثبت نمی‌شود.

**بررسی مرجع NexusPlatform:** در `EasyTraderBrokerClient.LoginAsync` (نسخهٔ `master` دیده‌شده هنگام بررسی، commit `da94cfc`) همان الگوی HTTP-based اجرا شده است: `HttpClientHandler` با `CookieContainer`, `AllowAutoRedirect=false`, دریافت authorize redirect، GET صفحهٔ Login، استخراج `__RequestVerificationToken`، POST فرم `Username`/`Password`/CSRF، دنبال‌کردن authorize callback، استخراج `code` و اعتبارسنجی `state`، سپس token exchange با `code_verifier` و `client_id` بدون `client_secret`. `EasyTraderOptions` مقدار پیش‌فرض `ClientId=easy_pkce`, `RedirectUri=https://d.easytrader.ir/auth-callback` و همان scope وب را تنظیم می‌کند. این کد یک راهکار عملیاتی در پروژهٔ ثالث نشان می‌دهد، اما callback آن همچنان callback سایت EasyTrader است؛ code از query redirect نهایی استخراج می‌شود و به callback محلی Trading_bot بازگردانده نمی‌شود. کد عمومی به‌تنهایی نه ثبت/اجازهٔ client را ثابت می‌کند و نه تضمین می‌کند این جریان در وضعیت جاری سرور همچنان کار کند.

**محدودیت‌های امنیتی مرجع:** در همین source، خطای POST ورود body HTML را در exception می‌گذارد و خطای token body را تا ۳۰۰ نویسه نگه می‌دارد؛ این رفتار ممکن است دادهٔ حساس/شخصی را لو دهد و نباید کپی شود. منطق same-login هر 2xx را می‌پذیرد، ولی شاخهٔ خاص 400 با متن `already logged in` در این capture مستند نشده است و نباید به قرارداد ما افزوده شود.

**امکان‌سنجی آفلاین عمومی:** یک فایل تست منفرد `test_generic_oidc_pkce_offline.py` در worktree Kilo ساخته شد که با server/session ساختگی، مکانیک عمومیِ cookie بین redirectها، CSRF ساختگی، استخراج code/state، PKCE و تبادل token بدون client secret را مدل می‌کند. این فقط نشان می‌دهد mechanics را می‌توان در fake transport مدل کرد؛ هیچ Mofid host یا قرارداد واقعی را اجرا/اثبات نمی‌کند. فایل هنوز در worktree Kilo است و به پروژهٔ اصلی منتقل نشده. اجرای تست به‌علت نبود دستور `python` در محیط در دسترس انجام نشد؛ نتیجهٔ تست تأیید نشده است.

پاسخ OIDC metadata زنده در نشست کاربر با HTTP 200 در دسترس بود. فهرست `token_endpoint_auth_methods_supported` در metadata شامل `client_secret_basic` و `client_secret_post` است و روش `none` در آن اعلام نشده است؛ همچنین metadata اعلام می‌کند PKCE از `plain` و `S256` پشتیبانی می‌کند. درخواست واقعی token exchange را فقط از نظر ساختار پاک‌سازی‌شده بررسی کردم: `POST /connect/token`, HTTP `200`; form keys برابر `grant_type`, `redirect_uri`, `code`, `code_verifier`, `client_id` بود؛ response keys/types برابر `id_token:string`, `access_token:string`, `expires_in:number`, `token_type:string`, `scope:string` بود. در request headers نمایش‌داده‌شده client `Authorization` وجود نداشت، و در فرم نیز `client_secret` نبود. این مشخص می‌کند مرورگر EasyTrader در همین نمونه secret نفرستاده؛ اما علت اینکه سرور با وجود metadata فاقد `none` این درخواست را قبول کرده، یا اینکه اعتبارسنجی بر اساس تنظیم client خاص دیگری انجام شده، از capture قابل استنتاج نیست. پاسخ موفق فقط رفتار همین client در همین جریان را ثابت می‌کند، نه مجازبودن client برای برنامهٔ ثالث.

در Trading_bot، `AuthenticationAdapter.begin_login(username, password)` الزاماً `LoginChallenge` برمی‌گرداند، ولی رابط حساب‌ها در حال حاضر فقط `CHALLENGE_CAPTCHA_IMAGE` را می‌پذیرد و `complete_login(response)` را با پاسخ متنی کپچا صدا می‌زند. این عدم تطبیق به مرحلهٔ ۳ (چالش) مربوط است و در این مرحله تصمیم‌گیری نمی‌شود.

با توجه به خواستهٔ مالک برای ورود مستقیم از فرم خود برنامه، بازکردن مرورگر و واردکردن رمز در صفحهٔ مفید مسیر موردنظر نیست. **آنچه اکنون روشن شد:** browser client در نمونهٔ زنده `client_id` را همراه code و PKCE verifier به token endpoint فرستاد، بدون `client_secret` یا client Authorization قابل مشاهده؛ سرور پاسخ 200 داد. پس از ورود، code به callback دامنهٔ خود EasyTrader (`d.easytrader.ir/auth-callback`) تحویل شد و همان برنامه آن را مصرف کرد. **آنچه capture روشن نمی‌کند:** چرا این client بدون روش `none` اعلام‌شده پذیرفته شد، آیا همین public client برای Trading_bot مجاز است، و آیا redirect URI دیگری برای دسکتاپ ثبت شده/پذیرفته می‌شود. این‌ها metadata/runtime capture به تنهایی حل نمی‌کند و نباید با آزمون callback جعلی یا بازپخش درخواست حدس زده شوند. تعبیهٔ client secret در برنامهٔ دسکتاپ امن نیست و راه‌حل محسوب نمی‌شود.

**پرسش:** آیا کلاینت دسکتاپ می‌تواند جریان authorize و callback را با روش امن و سازگار اجرا کند، یا کاربر باید در مرورگر وارد شود؟

**روش بررسی:** مستندات و کد موجود را با قرارداد فعلی برنامه تطبیق دهیم: بازکردن authorize، redirectها، callback، PKCE، مبدأهای مجاز و مرز نگهداری اسرار. هیچ redirect یا token exchange تازه‌ای برای آزمون اجرا نشود.

**خروجی لازم:** گزینه‌های فنی مجاز، پیش‌نیازهای هر گزینه، سازگاری با برنامهٔ فعلی، و تصمیمی که مالک پروژه باید بگیرد اگر بیش از یک مسیر معتبر باقی بماند.

**تصمیم مالک و مسیر منتخب:** کاربر اجازه داد Trading_bot جریان وب OIDC را با HTTP client بازسازی کند و code را از `Location` پیش از بارگذاری callback بگیرد؛ صفحهٔ callback وب نباید بارگذاری شود. این هم‌راستا با خواستهٔ ورود از فرم خود برنامه است و کپچا همچنان جداگانه در مرحلهٔ ۳ بررسی می‌شود.

**پیش‌نیاز پیش از هر اتصال واقعی:** اول تست generic کاملاً آفلاین باید ثابت کند redirect نهایی به callback درخواست نمی‌شود، `state` نامعتبر/غایب پیش از token exchange رد می‌شود، کوکی identity host به callback origin ارسال نمی‌شود، و token exchange PKCE بدون client secret ساخته می‌شود. تست فقط مکانیک عمومی را ثابت می‌کند، نه پذیرش فعلی مفید. سپس در پیاده‌سازی، URLهای redirect باید به hostهای مورد انتظار محدود شوند و code، state، verifier، رمز، CSRF، توکن و cookie در exception/log ذخیره نشوند. هیچ client secretی در برنامه قرار نمی‌گیرد.

**بازبینی نسخهٔ جاری تست:** Kilo تابع flow آفلاین را طوری اصلاح کرد که واقعاً `Location` را parse کند، `state` را پیش از token endpoint بررسی کند و در خطای generic متوقف شود. در اجرای دستی کاربر، نسخهٔ اول بعد از این اصلاح 1 passed و 1 failed شد؛ failure ناشی از assertion متناقض دربارهٔ cookie بود (یک assertion هم وجود و هم نبودن cookie در `oidc.invalid` را انتظار داشت). assertion اصلاح شد؛ Kilo گزارش داد focused pytest اکنون **2 passed in 0.08s**. من فایل نهایی را مستقلاً دیدم و تناقض برطرف شده، اما اجرای دوباره از محیط من ممکن نشد چون `python` روی PATH نیست؛ نتیجهٔ نهایی 2 passed فعلاً Kilo-reported است. هیچ اتصال یا درخواست واقعی مفید اجرا نشده است.

**نتیجهٔ ارزیابی فنی:** NexusPlatform یک روش قابل‌آزمایش و هم‌راستا با تصمیم مالک نشان داد: HTTP client با cookie jar، CSRF و PKCE؛ code از redirect گرفته می‌شود و callback صفحه‌ای بارگذاری نمی‌شود. خود Nexus در تنظیمات `easy_pkce` و redirect وب را دارد و شواهد اجرای مستقل یا پایداری این روش روی server فعلی نیست. بنابراین روش منتخب و اجازهٔ معماری روشن است؛ پذیرش runtime مفید هنوز فقط با اجرای محدود و صریحاً مجاز بعدی قابل تأیید است.

### 3. رفتار کپچا و چالش‌های ورود

**وضعیت: نوع چالش مشاهده‌شده؛ سیاست ظهور و اتصال به flow مستقیم باز است.** طبق مشاهدهٔ دستی کاربر در بررسی قبلی، صفحه ابتدا کپچا نداشت؛ پس از یک تلاش ورود با رمز اشتباه، کپچا ظاهر شد؛ تصویر کپچا یک بار refresh شد و سپس کاربر در همان صفحه با اطلاعات صحیح وارد شد. این یک نمونهٔ مشاهده‌شده است و ثابت نمی‌کند کپچا همیشه فقط بعد از اولین خطا ظاهر می‌شود یا در همهٔ نشست‌ها همین رفتار را دارد.

مستند تحقیق EasyTrader ساختار فرم را با فیلد `CaptchaInput` و دریافت تصویر از مسیر `/DNTCaptchaImage/Show` گزارش می‌کند؛ مقادیر CSRF/captcha نگهداری نمی‌شوند. شواهد موجود پاسخ POST کپچا یا رفتارهای ناموفق/انقضا/محدودشدن تلاش‌ها را ثبت نکرده‌اند. بنابراین نوع چالش تصویر کپچا است، اما قرارداد کامل refresh/validation آن هنوز نامشخص است.

در کد فعلی Trading_bot، `AccountsPage._begin_login` فقط `CHALLENGE_CAPTCHA_IMAGE` را می‌پذیرد و payload تصویر base64 را نشان می‌دهد؛ `complete_login` یک پاسخ متنی از کاربر دریافت می‌کند. در نتیجه UI فعلی از نظر نوع تعامل با کپچای تصویری سازگار به نظر می‌رسد، اما adapter مفید باید بتواند بفهمد کپچا در پاسخ فرم/redirect لازم شده، تصویر را به payload عمومی تبدیل کند، و `CaptchaInput` را در همان تلاش POST کند. کاربر برای refresh تصویر باید بتواند آن را دوباره دریافت کند یا تلاش را لغو و از نو شروع کند؛ قرارداد فعلی `LoginChallenge` فاقد عملیات refresh مستقل است.

**نتیجهٔ مرحله:** این مرحله را برای نوع اولیهٔ چالش می‌توان بست: «ممکن است کپچای تصویری در ورود مستقیم ظاهر شود و کاربر باید متن آن را دستی وارد کند». رفتار دقیق شرط ظهور، refresh، انقضا و پاسخ رد هنوز نامشخص است و باید در پیاده‌سازی adapter به‌صورت fail-closed مدیریت شود؛ کپچا یا محدودیت امنیتی دور زده نمی‌شود. این مرحله دربارهٔ OTP یا چالش دیگری شاهدی ندارد.

**پرسش:** کپچا/OTP یا تأیید اضافی در چه شرایطی ظاهر می‌شود و رابط برنامه چگونه باید آن را به کاربر واگذار کند؟

**روش بررسی:** از مستندات فعلی و captureهای طبیعی قبلی استفاده شود. وجود یک ورود موفق بدون کپچا را به نبود همیشگی کپچا تعمیم ندهیم. کاربر نباید مقدار کپچا، OTP یا رمز را برای گزارش بفرستد.

**خروجی لازم:** انواع چالش مشاهده‌شده، نقطهٔ ظهور، نیاز به تعامل کاربر، و رفتار امن هنگام لغو یا شکست؛ موارد مشاهده‌نشده جداگانه علامت‌گذاری شوند.

**معیار پایان:** قرارداد UI برای ادامه، لغو و خطای چالش تعریف شده باشد؛ اگر نوع چالش هنوز نامعلوم است، پیاده‌سازی وابسته به آن متوقف بماند.

### 4. معیار قطعی موفقیت ورود در برنامه

**پیشنهاد معیار fail-closed بر اساس شواهد فعلی:** adapter نباید صرفاً به‌خاطر HTTP 200 از token endpoint موفق برگردد. حداقل باید پاسخ JSON با `access_token:string` غیرخالی و `expires_in:number` معتبر بگیرد؛ سپس درخواست فعال‌سازی `same-login` با HTTP 200 و پاسخ خالیِ مشاهده‌شده موفق تلقی شود. پاسخ‌های خطا/ناشناخته، JSON ناقص یا پاسخ مبهم باید ورود را ناموفق/نامشخص نگه دارند و نشست را `LOGGED_IN` نکنند.

`startsession` در Network با HTTP 200 و پاسخ `{serverTime:string, startSessionTimeStamp:string}` مشاهده شده است، اما مدارک فعلی ثابت نمی‌کنند این endpoint برای ثبت هویت/اجازهٔ API ضروری است یا فقط نشست عملیاتی EasyTrader را راه می‌اندازد. بنابراین آن را فعلاً شرط قطعی `AuthenticationService.LOGGED_IN` نمی‌گذاریم؛ اگر broker adapter برای استفادهٔ API به آن نیاز دارد، باید به‌عنوان مرحلهٔ جداگانهٔ session activation با شرط schema خودش مدیریت شود. موفقیت HTTP 200 بدون بررسی body به‌تنهایی کفایت نمی‌کند.

در کد برنامه، `AuthenticationService.complete_login()` فقط وقتی `adapter.complete_login()` یک `AuthenticatedSession` برگشت بدهد، توکن را به SessionManager می‌دهد و وضعیت را `LOGGED_IN` می‌کند. مدل عمومی `AuthenticatedSession` به `access_token` و `user_identifier` غیرخالی نیاز دارد؛ شواهد فعلی Mofid وجود claimهای ممکن مانند `sub` را در metadata نشان می‌دهند، اما مقدار/claim واقعی ID token بررسی نشده است؛ پس نگاشت `user_identifier` هنوز باز است.

**وضعیت مرحله:** معیار orchestration برنامه مشخص شد: فقط adapter پس از تمام validationهای لازم می‌تواند session برگرداند؛ خطای مبهم باید fail closed باشد. قرارداد معنایی Mofid برای لزوم/ترتیب `same-login` و `startsession` و نگاشت user identifier هنوز نیازمند شواهد است.

**پرسش:** کدام شواهد کنار هم تأیید می‌کنند که ورود مفید واقعاً کامل شده است؟

**روش بررسی:** مراحل موجود را کنار هم بگذاریم: callback پردازش‌شده، token exchange موفق، پاسخ معتبر `startsession` و در صورت نیاز نتیجهٔ `same-login`. status HTTP به‌تنهایی موفقیت معنایی را ثابت نمی‌کند.

**خروجی لازم:** شرط‌های success، failure و indeterminate برای adapter عمومی برنامه و ترتیب ارزیابی آن‌ها.

**معیار پایان:** ورود ناقص یا پاسخ مبهم به‌اشتباه LOGGED_IN نشود و معیار به فیلدهای پاسخ مستند تکیه کند.

### 5. حداقل هویت و نام نمایشی حساب

**وضعیت مدل برنامه:** AccountStore حساب را با شناسهٔ داخلی یکتای برنامه، نام broker و `display_name` انتخابی کاربر نگه می‌دارد؛ مدل `Account` شناسهٔ برنامه را دارد و حساب کارگزاری را در خود embed نمی‌کند. صفحهٔ افزودن فعلی شناسهٔ داخلی تصادفی می‌سازد و credential را جداگانه در CredentialStore می‌گذارد؛ password/token وارد AccountStore نمی‌شود. بنابراین برای نمایش/تفکیک account در فهرست برنامه، فعلاً شناسهٔ مفید یا دادهٔ شخصی لازم نیست؛ display name را کاربر انتخاب می‌کند.

اما `AuthenticatedSession` عمومی برای adapterها `user_identifier` لازم دارد. Mofid metadata claimهای OIDC مثل `sub` و `preferred_username` را پشتیبانی‌شده اعلام می‌کند، ولی claimهای واقعی ID token در capture خوانده نشده‌اند و نمی‌دانیم کدام یک پایدار/غیرحساس است. کد NexusPlatform هم `OidcTokenResponse` را با `access_token`, `id_token`, `expires_in`, `token_type`, `scope` تعریف می‌کند، ولی هنگام ساخت EasyTraderSession فقط access token و expiry را نگه می‌دارد؛ بنابراین این مرجع user identifier را برای ما روشن نمی‌کند. برای کمینه‌سازی داده، از شناسهٔ داخلی برنامه برای account key استفاده می‌کنیم و هیچ claim شخصی را برای نام نمایشی لازم نمی‌دانیم؛ فقط باید بعداً ثابت شود `sub` یا یک شناسهٔ opaque مجاز و پایدار برای الزام adapter وجود دارد.

**تصمیم محصولی ثبت شد:** جریان استاندارد همان است که کاربر در صفحهٔ حساب‌ها «افزودن حساب» را می‌زند، broker را انتخاب می‌کند، نام کاربری، رمز و نام نمایشی را وارد و ثبت می‌کند؛ سپس از فهرست، حساب را انتخاب کرده و «ورود» را می‌زند. بنابراین افزودن حساب و احراز هویت دو اقدام جدا می‌مانند و ترتیب فعلی UI حفظ می‌شود؛ لاگین انجام نمی‌شود هنگام ذخیرهٔ فرم افزودن.

**پرسش:** برای نگهداری و نمایش حساب در Trading_bot به چه شناسهٔ پایدار و چه نامی نیاز است؟

**روش بررسی:** مدل Account و AccountRecord فعلی را با فیلدهای غیرحساس و مستند پاسخ ورود مقایسه کنیم. مقدار واقعی کاربر لازم نیست؛ فقط نام فیلد، نوع، پایداری و معنای آن بررسی شود.

**خروجی لازم:** حداقل دادهٔ لازم برای account key داخلی، نام نمایشی و association با broker؛ مشخص‌کردن اینکه آیا داده‌ای باید محرمانه نگهداری شود یا خیر.

**معیار پایان:** حساب مفید بدون اتکا به دادهٔ شخصی غیرضروری قابل تفکیک و نمایش باشد و سیاست ذخیره‌سازی هر دادهٔ محرمانه روشن باشد.

## دروازهٔ آغاز پیاده‌سازی

پس از حل این پنج مرحله، قرارداد موجود با authentication adapter، account store، broker manager و صفحهٔ حساب‌ها تطبیق داده شود. موارد حل‌نشده و تغییرهای لازم به مالک پروژه گزارش شوند. پیش از روشن‌شدن قراردادها و تأیید مالک، کدنویسی شروع نشود. هر مرحلهٔ بعدی باید تسک کوچک و مستقل داشته باشد؛ diff واقعی، فایل‌های تغییرکرده و نتیجهٔ تست‌های مرتبط جداگانه بازبینی شوند. این نقشه به‌تنهایی اجازهٔ تغییر معماری، استفاده از نشست واقعی، refresh، عملیات معامله‌ای یا صف ترکیبی کارگزاری‌ها نیست.

## وضعیت

- مرحلهٔ 1: تا حدی حل — یک پاسخ موفق `same-login` با HTTP `200` و body خالی مشاهده شد؛ status/بدنهٔ خطا نامشخص است.
- مرحلهٔ 2: معماری منتخب و مورد تأیید مالک — HTTP client، cookie jar، CSRF و PKCE؛ استخراج code از `Location` بدون بارگذاری callback. تست اصلاح‌شده به‌گزارش Kilo: 2 passed؛ کاربر پیش از اصلاح آخر 1 pass/1 failure (assertion متناقض cookie) گزارش کرد. نسخهٔ نهایی را مستقلاً بازبینی کردم؛ اجرای مستقل من به‌علت نبود Python روی PATH انجام نشد. این فقط mechanics ساختگی را پوشش می‌دهد و پذیرش فعلی مفید را اثبات نمی‌کند. کپچا مرحلهٔ ۳ است.
- مرحلهٔ 3: نوع چالش اولیه حل شد — کپچای تصویری پس از یک تلاش ناموفق در یک مشاهدهٔ دستی ظاهر و تصویر refresh شد؛ UI فعلی Trading_bot challenge تصویری/ورودی متن را می‌پذیرد. شرط ظهور عمومی، refresh/انقضا و schema پاسخ رد نامشخص است و باید در adapter به‌صورت fail-closed پوشش داده شود. شواهدی برای OTP نداریم.
- مرحلهٔ 4: تا حدی حل — orchestration برنامه روشن است: adapter فقط پس از validation موفق می‌تواند `AuthenticatedSession` بدهد و سرویس سپس `LOGGED_IN` می‌کند. token response باید ساختاری معتبر داشته باشد؛ `same-login` نمونهٔ موفق 200/بدنهٔ خالی است. لازم‌بودن/ترتیب معنایی `same-login` و `startsession` و نگاشت `user_identifier` برای Mofid هنوز شواهد می‌خواهد.
- مرحلهٔ 5: جریان محصولی و هویت نمایشی حل شد — افزودن حساب: انتخاب broker، ورود username/password و نام نمایشی، ثبت؛ سپس انتخاب حساب از فهرست و زدن Login. افزودن و login جدا هستند. AccountStore از شناسهٔ داخلی برنامه استفاده می‌کند و credential را جدا نگه می‌دارد؛ اطلاعات شخصی مفید برای نمایش لازم نیست. تنها بخش فنی باز این مرحله، یافتن claim غیرشخصی/پایدار برای `AuthenticatedSession.user_identifier` است؛ claimهای واقعی token در شواهد فعلی دیده نشده‌اند.
