# Handoff — ممیزی API و نشست EasyTrader

تاریخ: 2026-11-13

## محدوده و وضعیت فعلی

این تحویل فقط وضعیت مستندات ممیزی EasyTrader را خلاصه می‌کند. در تهیهٔ آن هیچ فایل یا داده‌ای از `Trading_bot` خوانده یا تغییر داده نشد و هیچ درخواست شبکه‌ای ارسال نشد. تمام تغییرهای ثبت‌شدهٔ این کار در پوشهٔ `EasyTrader-Audit/Documentation` هستند.

مرورگر ایزوله پس از اقدام دستی خروج، روی صفحهٔ ورود `login.emofid.com` قرار دارد. برای ادامهٔ بررسی APIهای خصوصی حساب و موجودی، کاربر باید در مرحلهٔ بعد شخصاً وارد شود؛ هیچ ورود خودکاری انجام نشود.

## احراز هویت و نشست

### پوشش `authentication.md`

یافته‌های مشاهده‌شدهٔ احراز هویت و نشست در `authentication.md` ثبت شده‌اند و شواهد Network از JavaScript جدا هستند:

- **Network:** دریافت metadata، redirectهای OIDC، فرم ورود با schema پاک‌سازی‌شده، مسیر callback، token exchange با schema پاک‌سازی‌شده، درخواست‌های `same-login` و `startsession`، وجود OIDC user در `sessionStorage` هنگام نشست، و خروج دستی با redirectهای end-session و بازگشت به صفحهٔ ورود.
- **JavaScript:** `signinRedirect` و callbackها، انتخاب storage بر اساس تنظیم، پشتیبانی library از silent renewal، `automaticSilentRenew:false` در تنظیم دیده‌شده، فراخوانی logout و شاخه‌های مدیریت 401/403.
- **مقادیر حساس:** password، CSRF value، code/state، Cookie، Authorization، JWT و token value در مستندات ذخیره نشده‌اند.

### موارد ناقص یا نامشخص احراز هویت

- تمدید طبیعی نشست و زمان/شرایط انقضا در Network مشاهده نشد.
- پاسخ `401/403` در Network آزمایش نشد؛ فقط رفتار کد مستند است.
- پس از logout پاک‌شدن storage مختص origin برنامه مستقیماً بررسی نشد؛ صفحه به دامنهٔ ارائه‌دهندهٔ ورود هدایت شده بود.
- body پاسخ endpoint logout و schema برخی پاسخ‌های ارائه‌دهنده بررسی نشده‌اند.
- مقادیر واقعی redirect عمداً حذف شده‌اند؛ نام پارامترها موجود است.

## تفکیک شواهد

تفکیک در اسناد رعایت شده است:

- `authentication.md`: بخش‌های مجزای «Network» و «JavaScript».
- `network-discovery.md`: شواهد درخواست/پاسخ واقعی و Schema پاک‌سازی‌شده؛ مواردی که فقط در bundle دیده شده‌اند با برچسب Code/JavaScript آمده‌اند.
- `api-catalog.md` و دسته‌بندی‌های حساب، نماد، ظرفیت و سفارش نیز میان مسیر قطعی در کد و مسیر مشاهده‌شده در شبکه تمایز می‌گذارند.

هیچ نمونه‌ای به‌عنوان قرارداد رسمی یا endpoint تأییدشده معرفی نشده مگر آن‌که در لاگ واقعاً مشاهده شده باشد.

## بررسی یافته‌های مهم قبلی

یافته‌های اصلی پیشین در اسناد ثبت شده‌اند:

- اختلاف شمار فایل‌های JavaScript: 58 فایل محلی در برابر 61 در گزارش اولیه؛ سه فایل همراه در dump اولیه نبودند. تاریخچهٔ بعدی 94 URL یکتای JavaScript را نشان داد که 36 مورد در دیسک محلی نبودند. این توضیح در `README.md` و گزارش Network آمده است.
- درخواست دستی سفارش ناموفق: پاسخ `POST /core/api/v2/order` با HTTP 200، `isSuccessful:false`، `omsError:null`، پیام خطای محدودهٔ زمانی و `id` خالی؛ اطلاعات در `network-discovery.md` و `orders.md` ثبت شده است.
- وضعیت نهایی بورس و حضور سفارش ناموفق در فهرست سفارش‌ها تأیید نشد؛ GETهای فهرست پیش از POST بودند و پس از آن GET فهرست در لاگ نبود.
- مسیرهای status سفارش که در bundle پیدا شدند از شواهد Network جدا و به‌عنوان کد-محور معرفی شده‌اند.
- یک POST دیگر در لاگ سفارش پس از درخواست قبلی دیده شد؛ بدنه/پاسخ آن عمداً بررسی نشده و این محدودیت در گزارش Network ثبت شده است.

در بازبینی این تحویل، یافتهٔ مهم شناخته‌شده‌ای از بررسی‌های قبلی پیدا نشد که کاملاً بیرون از مستندات مانده باشد. بااین‌حال، `README.md` پس از آخرین ورود/خروج دستی به‌روز نشده و یادداشت آن دربارهٔ صفحهٔ خالی/نیاز به ورود مجدد، وضعیت فعلی را منعکس نمی‌کند. جزئیات جدیدتر در `authentication.md` هستند.

## موارد تأییدشده، ناقص و نامشخص

### تأییدشده

- OIDC metadata، authorize redirect، فرم login، callback به `/auth-callback` و token exchange در Network با statusهای ثبت‌شده مشاهده شدند.
- API نشست برنامه (`same-login`, `startsession`) در Network مشاهده شد.
- در runtime پس از ورود، OIDC user entry در `sessionStorage` دیده شد؛ مقدارها خوانده یا ثبت نشدند.
- خروج دستی، `POST /easy/api/account/logout`, مسیر OIDC end-session و بازگشت به صفحهٔ ورود مشاهده شدند.
- پاسخ درخواست دستی سفارش به‌صورت backend failure ثبت شده؛ هیچ تأیید بورس مشاهده نشد.

### ناقص

- Schema برخی responseها و bodyهای نشست/logout عمداً یا به دلیل محدودیت لاگ بررسی نشده‌اند.
- README خلاصهٔ captureهای اخیر را ندارد.
- APIهای حساب/موجودی نیاز به تکمیل فیلدها، نوع داده‌ها، وابستگی‌ها و statusها دارند.

### نامشخص

- refresh واقعی، طول عمر نشست، انقضا و runtime responseهای 401/403.
- پاک‌شدن storage برنامه بعد از خروج.
- پذیرش/رد/اجرای سفارش در بورس و اینکه سفارش ناموفق در فهرست بعدی ظاهر می‌شود یا نه.
- ظرفیت خرید/فروش با شواهد شبکه و برخی schemaهای ردیف‌های حساب/سفارش.

## گام بعدی پروژه: تکمیل APIهای حساب و موجودی

1. ابتدا `account-and-balance.md`, `api-catalog.md` و بخش حساب در `network-discovery.md` را با هم تطبیق دهید.
2. مسیرهای موجود مانند `/easy/api/money`, `/assetmodule/api/performance` و `/option-asset/api/Assets/positions-profit-loss` را با داده‌های فقط‌خواندنی ثبت‌شده مستند کنید؛ هیچ endpoint دستی فراخوانی نشود.
3. برای schema یا statusهای ناقص، فقط درخواست‌های طبیعی رابط کاربری در مرورگر ایزوله را بررسی کنید. چون مرورگر پس از logout در صفحهٔ ورود است، قبل از مشاهدهٔ API خصوصی لازم است کاربر خودش اعلام آمادگی کند و دستی وارد شود.
4. مقادیر واقعی حساب، مانده، شناسه، token، Cookie و Authorization را حذف کنید؛ فقط Path, Method, Status, Content-Type, نام فیلدها و نوع داده را ذخیره کنید.
5. پس از تکمیل، شواهد Network را از مسیرهای JavaScript جدا نگه دارید و README را با وضعیت جدید همگام کنید.

## ذخیره‌سازی و داده‌های باقی‌مانده

- تغییرهای مستندات قبلی با موفقیت روی فایل‌ها نوشته شده‌اند؛ فهرست فایل‌ها و زمان تغییرشان در پوشه تأیید شد. این handoff نیز به‌عنوان فایل مستقل ذخیره شده است.
- هیچ HAR، cURL، body خام، token، Cookie، مقدار storage یا credential در این پوشه برای این handoff ایجاد نشده است.
- شواهد لازم برای ادامهٔ کار در اسناد هستند؛ هیچ یافتهٔ کلیدی از جریان login/logout فقط در حافظهٔ مکالمه باقی نمانده است. برخی مقادیر عمداً حذف شده‌اند و لاگ خام تاریخی قابل بازیابی نیست.
- در تهیهٔ این handoff هیچ فایل یا اطلاعاتی از `Trading_bot` استخراج یا تغییر داده نشد.
