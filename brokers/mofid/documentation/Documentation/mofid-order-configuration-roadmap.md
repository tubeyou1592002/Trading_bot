# نقشهٔ راه یکپارچه‌سازی پیکربندی سفارش مفید

## هدف

ثبت مراحل اتصال پیکربندی و ارسال سفارش حساب مفید به قابلیت‌های معتبر مفید، با حفظ مرز میان کارگزاری‌ها و جلوگیری از استفاده از داده‌های نامعتبر یا حدسی.

## برنامهٔ مرحله‌ای

1. **تعیین قابلیت‌های واقعی و شواهد — شواهد جریان خرید نمونه ثبت شد:** قراردادهای endpoint و محدودیت‌های زیر ثبت شده‌اند. موارد Network-observed از JavaScript-only و موارد unresolved جدا شده‌اند؛ این مرحله شواهد کامل همهٔ مسیرها نیست.
2. **اتصال جست‌وجو و شناسه:** `InstrumentProvider` مفید را ثبت کنید و جست‌وجوی نماد TSETMC را به ابزار مالی متناظر مفید با شناسهٔ دقیق و معتبر آن متصل کنید. در تطبیق مبهم یا نامنطبق، عملیات باید به‌صورت امن متوقف شود.
3. **اتصال جزئیات و محدودیت‌ها:** جزئیات و محدودیت‌های معتبر مفید را متصل کنید. محاسبه‌گر ظرفیت مخصوص نماد را بررسی کنید؛ قدرت خرید کل حساب را جایگزین آن نکنید و در صورت پشتیبانی‌نشدن، این وضعیت را صریح اعلام کنید.
4. **اتصال ارسال سفارش:** ارسال سفارش مفید را متصل کنید و اطمینان دهید برای حساب مفید هیچ API آگاه فراخوانی نمی‌شود. پاسخ اولیه و خطاها را به کاربر نمایش دهید.
5. **تغییر حساب:** بررسی کنید تغییر حساب، نماد، شناسه و محاسبات وابسته به کارگزاری قبلی را پاک می‌کند و در صورت نبود دادهٔ معتبر، عملیات به‌صورت امن متوقف می‌شود.
6. **اعتبارسنجی و انتقال:** آزمون‌های خودکار، بازبینی و تأیید دستی کنترل‌شده انجام شود. انتقال بعدی از Kilo به محیط اصلی و هم‌ترازی فقط پس از تأیید جداگانه انجام شود.

## شواهد فنی و وضعیت

- **Network-observed — شناسهٔ ابزار TSETMC:** الگوی `GET https://cdn.tsetmc.com/api/Instrument/GetInstrumentInfo/{insCode}`؛ فیلدهای پاسخ شامل `insCode` (شناسهٔ عددی ابزار TSETMC)، `instrumentID` (ISIN ابزار مورد استفادهٔ مفید)، `cIsin` (ISIN شرکت) و برچسب‌ها هستند. این شناسه‌ها معانی متفاوت دارند. در یک تطبیق نمونه، ISIN مفید با TSETMC `instrumentID` برابر بود؛ این نتیجه فقط مختص نمونهٔ بررسی‌شده است.
- **Network-observed — جزئیات نماد انتخاب‌شده:** `POST /symbols/api/MarketData/symbol-info-data` با body به‌شکل `{isin}` پاسخ HTTP 200 داد. schema شامل `symbolISIN`، `highAllowedPrice`، `lowAllowedPrice`، `closingPrice`، `lastTradedPrice`، `EPS`/`PE` و معیارهای عمومی مرتبط نماد است.
- **Network-observed — دادهٔ بازار:** `POST /symbols/api/marketdata/v2` با آرایه‌ای از ISINهای نمادها در body پاسخ HTTP 200 داد. schema هر نماد شامل `symbolIsin`، `highAllowedPrice`، `lowAllowedPrice`، `minValidBuyVolume`، `maxValidBuyVolume`، `minValidSellVolume`، `maxValidSellVolume`، `priceTickSize`، `stateCode`/`symbolState`، قیمت‌ها و مقادیر بازار است.
- **Network-observed — ثبت سفارش:** `POST /core/api/v2/order` با envelope JSON به‌شکل `{order:{price,quantity,side,validityType,createDateTime,commission,symbolIsin,symbolName,orderModelType,totalValue,orderFrom}}` پاسخ HTTP 200 داد. schema پاسخ `{isSuccessful:boolean,id:string,message:string,omsError:null-or-value}` است. HTTP 200 به‌تنهایی پذیرش سفارش را اثبات نمی‌کند؛ پاسخ مشاهده‌شده می‌تواند `isSuccessful=false`، شناسهٔ خالی، پیام اعتبارسنجی و `omsError` تهی داشته باشد.
- **Network-observed — قدرت خرید حساب:** `GET /easy/api/money` پاسخ شامل `buyPowerT2` است. برنامه از adapter متصل به حساب فعال برای خواندن قدرت خرید استفاده می‌کند.
- **Network-observed — دادهٔ محاسبه:** `/symbols/api/symbols/all` شامل `buyCommission`، `hidePrice`، `csize` و `minDealableCount` است؛ `/symbols/api/marketdata/v2` شامل `buyRatio` و `maxValidBuyVolume` است.
- **JavaScript-only — محاسبهٔ تعداد/مجموع:** EasyTrader از `floor(amount/(price*(1+commission)+hidePrice)/csize)`، سقف نماد و مضرب حداقل استفاده می‌کند؛ مجموع با ceil محاسبه و fee اختلاف آن با مبلغ پایه است.
- **JavaScript-only — مسیر قدرت خرید نماد:** مسیر `GET /orders/api/order/money/order-entry?symbolIsin=...` در JavaScript وجود دارد؛ پاسخ به‌صورت `buyingPower` به‌علاوهٔ مجموع `credits[].amount` مصرف می‌شود. درخواست/پاسخ زمان اجرا مشاهده نشده است. ارتباط این مسیر با محاسبه‌گر تعداد تأیید نشده است.
- **Unresolved — جست‌وجوی نماد:** درخواست جست‌وجوی نماد به‌ازای query ثبت نشده است. `/symbols/api/symbols/all` فهرست bulk است و اثبات‌کنندهٔ جست‌وجوی queryمحور نیست.
- **Unresolved — پوشش مسیر سفارش:** شواهد UI زمان اجرا فقط یک مسیر خرید سهام عادی را پوشش می‌دهد؛ مسیر فروش و دسته‌های دیگر محصول تأیید نشده‌اند.

## گام بعدی

وضعیت پیاده‌سازی (2026-11-20): شناسهٔ نماد و فیلدهای قیمت‌گذاری از provider مفیدِ متصل به adapter حساب فعال حل می‌شوند. Provider، `buyCommission` را از catalogue و `buyRatio` را از market response به‌صورت Decimal متناهی و نامنفی اعتبارسنجی می‌کند. نسبت و کمیسیون در شواهد نمونه با واحدهای قابل‌مقایسه تأیید نشده‌اند؛ بنابراین آن‌ها مقایسه نمی‌شوند و calculator فقط از `buyCommission` استفاده می‌کند. Bounds بازار فرم از همان `BrokerInstrument` بارگذاری می‌شود. ماشین‌حساب از قدرت خرید حساب مفید (`buyPowerT2`) و فرمول مستند JavaScript استفاده می‌کند؛ نتیجهٔ پیش‌نمایش جایگزین ظرفیت سفارش/ارسال نیست. هیچ سفارش ارسال نمی‌شود. رفتار runtime واقعی نیازمند بررسی کنترل‌شده است.

وضعیت اجرا (2026-11-20): provider فیلدهای قیمت/حجم و `buyCommission` و `buyRatio` را نگه می‌دارد؛ دادهٔ قیمت‌گذاری نامعتبر با توقف امن رد می‌شود. نتیجهٔ قدیمی حساب/نماد رد می‌شود و تأیید فقط قیمت و تعداد فرم را پر می‌کند، نه ارسال سفارش. مسیر Agah مجزا باقی است. آزمون‌ها آفلاین‌اند؛ رفتار runtime واقعی هنوز نیازمند بررسی کنترل‌شده است.

اصلاح محاسبه: ظرفیت ابتدا floor می‌شود، سپس سقف اعمال و مقدار به مضرب بالاتر کمینه گرد می‌شود. مجموع با ceil محاسبه و در صورت عبور از بودجه یا قدرت خرید رد می‌شود؛ تعداد کاهش داده نمی‌شود. محاسبهٔ خودکار نیز قدرت خرید حساب را دریافت می‌کند. رابطه/واحد دقیق `buyRatio` با `buyCommission` از نمونه‌های مشاهده‌شده قابل اثبات نیست؛ نسبت فقط برای تشخیص نگه داشته می‌شود و در محاسبه دخیل نیست.

## معیارهای تکمیل

- شواهد و موارد نامشخص قابلیت‌های مفید ثبت شده‌اند و دادهٔ حدسی استفاده نمی‌شود.
- نماد، شناسه، جزئیات، محدودیت‌ها و ظرفیت بر اساس دادهٔ معتبر مفید استفاده می‌شوند؛ ابهام و قابلیت پشتیبانی‌نشده به‌صورت امن مدیریت می‌شوند.
- سفارش حساب مفید فقط از مسیر مفید ارسال و پاسخ یا خطا نمایش داده می‌شود؛ تغییر حساب داده‌های وابستهٔ قبلی را پاک می‌کند.
- آزمون‌های خودکار، بازبینی و تأیید دستی کنترل‌شده انجام شده‌اند؛ انتقال و هم‌ترازی با محیط اصلی منوط به تأیید بعدی است.
